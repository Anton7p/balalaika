# Вариант A: одна панель 3x-ui, несколько Xray на разных машинах

Цель: панель управления только на **master**; на **nodes** — агент/Xray (или node-режим 3x-ui), синхронизация инбаундов и клиентов через панель. Бот и приложение продолжают опираться на **одну** точку входа в API панели (`VPN_PANEL_URL` на мастере), а выдача конфигов пользователю учитывает выбранную ноду.

## Текущее состояние репозитория (контекст)

- Инвентарь CI уже поддерживает `INVENTORY_MODE=cluster` и группу `[nodes]` (`ansible/playbooks/ci-write-inventory.yml`, `ansible/playbooks/templates/inventory.ci.ini.j2`).
- `ansible/playbooks/deploy.yml` таргетит только `hosts: master`; отдельного play для нод нет.
- В приложении: один лейбл ноды через `WHITE_LABEL_NODE_ID`, `listNodes` в провайдере 3x-ui — заглушка (`src/vpn/load-balancer.service.ts`, `src/vpn/three-x-ui-vpn.provider.ts`).

## Архитектура варианта A

1. **Master** — веб-панель 3x-ui, nginx/TLS на домене (как сейчас), опционально подписка и бот на том же хосте.
2. **Nodes** — машины с Xray (через агент 3x-ui или минимальный compose под вашу версию панели); открыты только нужные VPN-порты и канал к панели.
3. **Панель** хранит конфигурацию и распределяет её на привязанные ноды (механизм зависит от версии 3x-ui; перед автоматизацией зафиксировать шаги из официальной документации под вашу сборку).

## Панель не в пути пользовательского VPN

Это тот же вариант A, но с явным разделением **управления** и **данных**:

| Что | Куда ходит трафик |
|-----|-------------------|
| **Пользовательский VPN** (VLESS/REALITY и т.д.) | Напрямую на **ноду** (или на тот хост, где реально слушает inbound Xray): IP/DNS и порт из выданного конфига. Веб-порт панели (**`/panel/`**, API) **не** используется как транспорт VPN. |
| **Панель** | Только UI администратора, API создания клиентов, синхронизация конфигов на агенты нод. Объём — HTTPS и служебные каналы панель ↔ агент, не массовый пользовательский туннель. |
| **Бот приложения** | HTTP(S) к **`VPN_PANEL_URL`** — это вызовы API панели (логин, `addClient` и т.д.), не VPN-пейлоад пользователя. |
| **Подписка** (если включена) | Обычно отдельный HTTP(S) запрос клиента за текстом подписки; это не то же самое, что туннель VPN через порт панели. |

Практический вывод для проектирования:

- На **master** в продакшене можно **не открывать наружу** порт инбаунда Xray, если все пользователи заведены только на нодах: наружу — домен панели/подписки/бота, а VPN — только IP/имена нод.
- На **нодах** наружу — SSH (по политике), порт(ы) VPN; до панели — только то, что нужно агенту (часто исходящее на URL/API мастера).

Итог: «не пускать трафик через панель» в нормальной схеме 3x-ui означает **не использовать хост панели как точку входа VPN для клиентов**; управление остаётся на панели, данные — на нодах (или на выделенном edge, если позже вынесете инбаунд отдельно).

## Слой Ansible

- Новый play **`hosts: nodes`** (или роль `node`), например `ansible/playbooks/deploy-nodes.yml`:
  - директория деплоя, Docker/compose при необходимости;
  - firewall (ufw/nftables) — только SSH, порт(ы) VPN, при необходимости исходящие к панели;
  - переменные из секретов CI: URL панели (или внутренний адрес), токен/API-ключ для присоединения ноды, при необходимости отдельные REALITY-ключи на ноду.
- Контракт **INFRASTRUCTURE_IP_LIST**: как сейчас — массив строк или объектов `{ "address", "password" }`; при необходимости расширить полями `region`, `vpn_port` без поломки парсера в `ci-write-inventory.yml`.
- Порядок в CI: `bootstrap` (уже `hosts: all`) → деплой мастера (`deploy.yml`) → деплой нод (`deploy-nodes.yml`), с явными зависимостями job’ов.

## Регистрация ноды в панели

- **MVP:** один раз в UI панели добавить ноду по инструкции upstream; Ansible только ставит софт и открывает порты.
- **Автоматизация:** после `POST …/login` и cookie-сессии вызывать API панели для добавления ноды (эндпоинты и поля — только под вашу версию 3x-ui; зафиксировать в `docs/AGENT_INFRA.md` или отдельном разделе). В репозитории действует правило: **без CSRF**, только cookie после логина.

Решить заранее:

- один общий inbound, синхронизируемый на все ноды, или отдельные порты/REALITY на каждой ноде;
- откуда берётся keypair REALITY (один на кластер или на ноду) — см. текущие задачи вроде `ansible/playbooks/tasks/deploy/three-x-ui-inbound/reality-keypair-generate.yml`.

## DNS и доступ пользователя

- **Проще:** отдельный hostname на ноду (например `nl.example.com`, `de.example.com`) — в connection URI подставляется адрес выбранной ноды.
- **Сложнее:** один внешний hostname и балансировка/SNI на edge — отдельный проектный блок (не обязателен для первого этапа).

## Изменения в приложении (Nest)

1. **`LoadBalancerService`** — список нод из конфига (id, вес, `enabled`, опционально регион); политика: round-robin, random или sticky по `telegramUserId`.
2. **`ThreeXUiVpnProvider`** — при создании клиента учитывать выбранную ноду, если API панели это поддерживает для подключённых nodes; иначе договориться о семантике «один inbound — панель сама пушит на ноды».
3. **`listNodes`** — реальный список из API панели или из статического конфига env, если API не покрывает нужные поля для админки.

Метки клиентов (`label` при создании в 3x-ui) лучше зафиксировать в одном формате (например `nodeId:planMonths`) для поддержки и отзыва.

## CI и секреты

- Сохранить/добавить секреты: данные для join ноды к панели, при необходимости отдельные пароли SSH по нодам (шаблон инвентаря уже допускает пароль на элемент списка).
- Не коммитить `inventory.ini` с паролями.

## Документация и эксплуатация

Зафиксировать отдельно (чеклист):

- матрица портов: панель, VPN, subscription;
- процедура добавления новой ноды;
- поведение при падении ноды (исключение из балансировки в конфиге или ручной флаг).

## Порядок внедрения (рекомендуемый)

1. Вручную подключить вторую машину к панели по документации вашей версии 3x-ui; записать точные шаги и при необходимости HTTP-запросы.
2. Перенести установку на ноде в Ansible (`hosts: nodes`) + health check с мастера.
3. Заменить заглушки балансировки и `listNodes` в приложении.
4. Прогнать e2e: покупка/выдача конфига, админ-статус нод.
