# VPN: канонические правила (master, ноды, пулы, failover, бот)

Один документ задаёт **как мы ведём сервис**: учёт и API на **master**, трафик пользователей на **нодах**, пулы **рабочих** и **запасных** нод, переключение по **варианту A** (API + рассылка `vless://`). Прямых правок SQLite панели вручную нет.

См. также: **[`PANEL_MASTER_NODES.md`](PANEL_MASTER_NODES.md)** (версии, Ansible), **[`VPN_NODES_AND_FAILOVER.md`](VPN_NODES_AND_FAILOVER.md)** (кратко про inbound и бота), **[`PANEL_REST_API.md`](PANEL_REST_API.md)** (REST), **[`3XUI_CLIENT_MANAGEMENT.md`](3XUI_CLIENT_MANAGEMENT.md)** (UI панели).

---

## 1. Канонические правила

1. **Master (3x-ui)** — единственная «правда» по учёту: inbounds, клиенты, сроки, лимиты, ноды в разделе **Nodes**. Доступ бота к панели — **только HTTP API** (сессия UI или Bearer), без SQL в БД панели.
2. **Публичный домен master** (`DOMAIN_NAME`, nginx, TLS) используется для **админки и автоматизации** (Ansible с контроллера, при необходимости — HTTPS к панели). В **пользовательском `vless://` и в ссылках для людей** домен master **не используем** как обязательную точку входа трафика.
3. **Ноды** — точка входа **пользовательского трафика** (IP ноды или отдельное имя, если вы сознательно повесите DNS на ноду; это уже внешнее решение). На ноде крутится **3x-ui + Xray** (тот же образ/версия, что и на master).
4. **Пулы нод:** ведём **список рабочих** (сейчас несут или готовы нести прод-трафик через свой inbound на master с `nodeId`) и **список запасных** (подняты Ansible, зарегистрированы на master, inbound есть, клиентов нет или минимум для прогона). **Пары 1:1 «рабочая + своя страховая» не обязательны** — при инциденте берём **любую подходящую свободную** из запаса.
5. **Выдача пользователю** — основной формат **`vless://…`**: адрес и порт — **эндпоинт ноды** (и параметры REALITY из панели). Подписка **`/sub/…`** не является целевым форматом выдачи; если когда-то понадобится подписка — только с **ноды** или отдельного хоста, **не** как обязательная ссылка на master.
6. **Поведение бота:** **новые** клиенты — в первый **рабочий** inbound из **`VPN_WORKING_INBOUND_IDS`**, у которого число клиентов **&lt; `VPN_INBOUND_CLIENT_LIMIT`**; **продление** — всегда в тот же inbound, что при выдаче (**`panel_inbound_id`** в Postgres). Пользователю — **`vless://`** после `addClient` / `updateClient` (`src/vpn/three-x-ui-vpn.provider.ts`, `src/vpn/load-balancer.service.ts`). Сессия 3x-ui v3: CSRF + cookie (см. [`AGENT_INFRA.md`](AGENT_INFRA.md), Ansible `include-panel-ui-session-bearer.yml`).

## 2. Роли компонентов

| Компонент | Роль |
|-----------|------|
| **Master** | Учёт, API, привязка inbound к ноде через **`nodeId`**. Не светим пользователям как обязательный домен в конфиге VPN. |
| **Ноды** | Исполнение Xray для inbound’ов с **`nodeId`**. Публичные **IP** (и порты из Ansible) — норма для клиентских конфигов. |
| **Бот (Nest)** | Только API master; хранение подписок в **Postgres**; при смене ноды/inbound — **рассылка новых `vless://`**. |
| **Ansible** | Поднимает master и ноды, per-node inbound, UFW. **Не** заменяет мониторинг и массовую рассылку. |

## 3. Пулы «рабочие» и «запасные»

- **Рабочие:** для каждой ноды из списка на master есть inbound с **`nodeId`** (после `deploy-nodes.yml`). Их id перечислены в **`VPN_WORKING_INBOUND_IDS`** (порядок = приоритет для **новых** клиентов).
- **Запасные:** online, inbound есть, **без массы прод-клиентов**; в env бота **не** перечисляются — только операторский runbook и §6. При падении **любой** рабочей берётся **свободная запасная**, `copyClients`, рассылка **`vless://`**.

Ведите для операторов маленькую таблицу: **имя хоста / IP / id inbound в UI / id ноды в UI / пул (рабочий|запас)**.

### 3.1. Три смысла (не три обязательных сервера)

| Понятие | Смысл |
|---------|--------|
| **Рабочая нода** | Через неё уже идёт (или может идти) прод-трафик: на master есть inbound с **`nodeId`** этой ноды, в нём есть или будут клиенты. Рабочих может быть **несколько** (несколько inbound’ов). |
| **Запасная нода** | Готова к failover: online, inbound есть, **без массы прод-клиентов**. |
| **Приём новых клиентов** | Не отдельный сервер. Бот на каждую **новую** подписку выбирает **первый** id из **`VPN_WORKING_INBOUND_IDS`**, где клиентов **&lt; лимита**. |

Много **клиентов** в одном inbound — у каждого **свой** `vless://`. Много **inbound’ов** — обычно **один per-node** после Ansible.

### 3.2. Состояния рабочей ноды (логика операций)

| Состояние | Новые подписки | Существующие клиенты | В запасной пул? |
|-----------|----------------|----------------------|-----------------|
| **Принимает новых** | Да (пока count &lt; лимит) | Да | Нет |
| **Заполнена (лимит)** | Нет → следующая рабочая в списке | Да, без смены `vless://` | **Нет** |
| **Мёртвая / выведена** | Нет | После failover — на другом inbound | — |

**Запасная** одно состояние: **готова**, в ротации по лимиту **не участвует**.

### 3.3. Два сценария (не путать)

| Событие | Действие | Рассылка `vless://` |
|---------|----------|---------------------|
| **Лимит клиентов** на рабочей | Следующий id в **`VPN_WORKING_INBOUND_IDS`**; заполненная остаётся **рабочей** | Не нужна для старых |
| **Авария ноды** | Запасная, **`copyClients`**, обновить список рабочих / id в env, §6 | **Обязательна** перенесённым |

## 4. Лимит клиентов и список рабочих inbound

**Автоматика в боте:** перед **`addClient`** считаются клиенты в каждом inbound из **`VPN_WORKING_INBOUND_IDS`**; выбирается первый с count **&lt; `VPN_INBOUND_CLIENT_LIMIT`**. Если все полны — ошибка выдачи (нужна новая рабочая нода в списке или выше лимит).

**Ручная смена списка:** правка **`ansible/bot/defaults/main.yml`** или `.env` на master → деплой бота. **Новые секреты GitHub не добавляем** ([`GITHUB_SECRETS.md`](GITHUB_SECRETS.md)).

### 4.1. Рекомендуемый критерий для старта — **число клиентов** в текущем inbound

- Проще, чем сразу CPU/канал: считаете клиентов через **API / UI** панели.
- **Порог для теста:** **1** или **2** клиента достаточно для смоука (порог **2** нагляднее: два клиента на старом inbound, сменили id — третья регистрация должна попасть в новый inbound).
- **Прод:** пороги **сотни и выше**, иначе будете дёргать id из‑за шума. Точное число — от ёмкости ноды и продукта.

### 4.2. Гистерезис и процесс

- Не реагировать на один всплик: например «клиентов ≥ N **и** решение зафиксировано» или «CPU высокий **дольше M минут**», если позже добавите метрики с ноды.
- Перед сменой: следующий inbound **готов** (нода online, `nodeId` верный).
- После смены: **мониторинг** ошибок панели/бота; старый inbound **не удалять** сразу — откат возможен.
- Inbound выдачи хранится в **`subscriptions.panel_inbound_id`** (продление не уезжает на «следующую» ноду).

### 4.3. Масштабирование без падения ноды

- **Новая нода:** **`NODE_IPS`** → **`deploy-nodes`** → дописать id в **`VPN_WORKING_INBOUND_IDS`** (в конец или в начало списка по политике).
- **Только новые на новую ноду:** достаточно порядка в списке и лимита; старые остаются на своём inbound (**`panel_inbound_id`**).
- **Разгрузить старую:** часть клиентов **`copyClients`** на inbound новой ноды + рассылка новых ссылок; два inbound с клиентами могут сосуществовать.

### 4.4. Почему панель сама не «выдаёт свободную ноду» на `addClient`

**Balancer в Xray** не выбирает ноду для **`addClient`**. Выбор inbound для новых — **бот** (`LoadBalancerService` + API панели).

## 5. Домен и блокировки

- Блокировка **домена master** бьёт по **админке, подпискам и ссылкам, где этот домен фигурирует**. Поэтому пользовательский трафик строим на **IP/имени ноды**, не на домене панели.
- Блокировка **IP ноды** или сигнатуры протокола решается **сменой ноды** и новыми **`vless://`**, а не сменой только DNS на master.

## 6. Failover (вариант A)

### 6.0. Автоматика: контейнер `vpn-watchdog` на master

На master в compose бота ([`ansible/bot/templates/app-compose.yml.j2`](../ansible/bot/templates/app-compose.yml.j2)):

| Сервис | Роль |
|--------|------|
| **`vpn-watchdog`** | Тот же образ, что `app`; `node dist/watchdog/main.js`; `restart: always` |
| **`app`** | `POST /internal/vpn/failover` — обновление подписок в Postgres, Telegram, Redis-список рабочих inbound |

**Проверка (каждые `VPN_WATCHDOG_INTERVAL_SEC`, по умолчанию 60 с):** для каждой ноды из **`VPN_WATCHDOG_NODES_JSON`** с `"pool":"working"` — TCP на `host:port` (VPN-порт inbound); при заданном **`panelNodeId`** — ещё `POST …/nodes/probe/:id`. **`fail_threshold`** подряд (по умолчанию 3) → failover.

**Failover:** первая живая нода с `"pool":"standby"` → `copyClients` на master → отключение мёртвого inbound → hook бота → рассылка новых **`vless://`**.

Конфиг watchdog — в **`.env`** на master (шаблон [`app.env.j2`](../ansible/bot/templates/app.env.j2), дефолты [`ansible/bot/defaults/main.yml`](../ansible/bot/defaults/main.yml)): **`VPN_WATCHDOG_NODES_JSON`**, пороги, **`VPN_WATCHDOG_HOOK_SECRET`** (можно = `ENCRYPTION_KEY`). **Не** секреты GitHub.

После авто-failover список **`VPN_WORKING_INBOUND_IDS`** для **новых** клиентов дублируется в Redis (`balalaika:vpn:working_inbound_ids`); бот читает Redis, затем env.

### 6.1. Ручной failover (если watchdog выключен)

Порядок действий:

1. **Мониторинг** (вне приложения): TCP до VPN-порта ноды, при необходимости статус ноды на master, **гистерезис** против флапа.
2. Подтвердить инцидент; выбрать **запасную** ноду (online, есть inbound с нужным `nodeId`).
3. Через API master: **`copyClients`** (или актуальный метод из **API Docs** вашей панели) с **мертвого** inbound на **inbound запасной** ноды. Проверить клиентов в UI.
4. **Отключить** старый inbound или оставить выключенным, чтобы трафик не уходил в мёртвую ноду.
5. Обновить **`VPN_WORKING_INBOUND_IDS`** (заменить id мёртвой ноды на id запасной); деплой/рестарт бота.
6. Для каждой активной подписки в **Postgres**: получить актуальный **`vless://`** из API; **массовая рассылка** в Telegram (батчами).
7. Обновить внутренние списки: какая нода теперь в пуле **рабочих**, пополнить **запас** при следующем Ansible-прогоне.

**Важно:** сценарий «тот же inbound id, только сменили **`nodeId`** одним `update`» на 3x-ui **не опираемся** — на практике не подтверждён (см. историю проверок в репозитории). Опора — **новый inbound + `copyClients` + смена `VPN_PANEL_INBOUND_ID`**.

Запасные сценарии из API (деталь): **`copyClients`**; либо восстановление клиентов из **БД бота** через **`addClient`**, если копирование недоступно.

## 7. Бот и переменные

| Переменная | Где задаётся | Смысл |
|------------|--------------|--------|
| **`VPN_PANEL_URL`** | `.env` на master (шаблон `ansible/bot/templates/app.env.j2`) | API master для бота |
| **`VPN_WORKING_INBOUND_IDS`** | `ansible/bot/defaults/main.yml` → `.env`; локально — корневой `.env` | Рабочие inbound id через запятую, **порядок = приоритет** |
| **`VPN_INBOUND_CLIENT_LIMIT`** | то же | Лимит клиентов на inbound (смоук: **1–2**, прод: **сотни**) |
| **`VPN_PANEL_INBOUND_ID`** | опционально | Устаревший один id, если список рабочих не задан |
| **`VPN_ADMIN_*`** | GitHub Secrets → `.env` | Логин панели (секрет) |
| **`DOMAIN_NAME`** | GitHub Secrets | TLS/nginx master, не endpoint VPN в `vless` |

**Не в GitHub Secrets:** пулы, лимиты, списки inbound — только репозиторий + `.env` на сервере.

**Postgres:** `subscriptions.panel_inbound_id` — inbound выдачи для продления.

## 9. Чеклист при инциденте

1. Подтвердить падение/блок (пробы + панель).
2. Выбрать запасную ноду из пула.
3. `copyClients` (или эквивалент) → проверка UI.
4. Обновить **`VPN_WORKING_INBOUND_IDS`**, рестарт бота.
5. Выдать и разослать **`vless://`**.
6. Обновить документацию операторской таблицы пулов; при необходимости — новый хост в **`NODE_IPS`** и повторный **`deploy-nodes`**.

## 10. Версионность

Поведение API и **`nodeId`** зависит от версии **3x-ui**. Репозиторий целится в **v3.0.2**; после обновления панели перечитать встроенные **API Docs** и при необходимости обновить этот файл.
