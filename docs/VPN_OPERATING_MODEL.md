# Целевая модель: ноды, master, выдача vless, failover (без правок БД панели вручную)

Один документ фиксирует **как мы планируем** вести VPN-сервис: через **HTTP API 3x-ui**, без прямых SQL в SQLite панели. Остальные детали Ansible и API см. [`PANEL_MASTER_NODES.md`](PANEL_MASTER_NODES.md), [`PANEL_REST_API.md`](PANEL_REST_API.md), [`VPN_NODES_AND_FAILOVER.md`](VPN_NODES_AND_FAILOVER.md).

---

## Роли

| Компонент | Роль |
|-----------|------|
| **Master (3x-ui)** | Единственная «правда» по учёту: inbounds, клиенты, сроки, лимиты. **Не светится** пользователям: нет публичных ссылок на master-домен в клиентских конфигах и подписках для людей. |
| **Ноды (3x-ui + Xray)** | Публичные **IP нод** — нормальная точка входа трафика. Панель ноды может быть только для админа или с ограниченным ACL. |
| **Бот (Nest)** | Создание/продление клиентов **только через API** master. Пользователю отдаёт **`vless://`** (без обязательной подписки и без «мороки» с доменом под `/sub/`, если так решено продуктово). При смене ноды — **короткое сообщение** с новой ссылкой. |

---

## Выдача пользователю

- Основной формат: **`vless://…`** (адрес = IP или домен **ноды**, порт VPN, REALITY и т.д.).
- Подписка (`/sub/…`) **не обязательна**; если понадобится — только с **ноды** или с отдельного хоста, **не** с master.

---

## Пул нод и здоровье

- В инвентаре / конфиге: **активная** нода(ы) для выдачи и **запасные**, уже поднятые (Ansible), зарегистрированные на master.
- **Проверка «нода жива»**: не один ping; минимум TCP до VPN-порта и/или статус ноды в панели master + при необходимости пробы с той среды, где крутится мониторинг (чтобы не ловить ложные «up»).
- **Гистерезис**: не переключать при одном флапе; порог по времени/числу ошибок — чтобы не спамить новыми ссылками.

## Переезд при падении / блоке ноды

### Желаемая идея (минимум действий)

**Один inbound на master** с привязкой к ноде (`nodeId`), в нём все клиенты. При аварии **сменить только привязку к другой ноде**, UUID/сроки/лимиты клиентов **не трогать** — дальше пересобрать и раздать новый **`vless://`** (IP/порт REALITY на новой ноде могут отличаться).

### Проверка по исходникам 3x-ui (**v3.0.x**, наблюдения сверяли с **v3.0.1**)

В `InboundService.UpdateInbound` в ветке обновления **не видно** присвоения `NodeID` из тела запроса в сохраняемую строку inbound (копируются remark, port, settings, streamSettings и т.д., но не `nodeId`). В `web/controller/inbound.go` для `updateInbound` есть комментарий, что **Phase 1 не поддерживает миграцию inbound между нодами**.

**Проверка на живой панели:** `POST …/inbounds/update/1` с телом, где `nodeId` равен id ноды из `nodes/list`, вернул `success: true`, но повторный `GET …/inbounds/get/1` показал **`nodeId` по-прежнему `null`** (локальный inbound). То есть **привязка к ноде через этот вызов не применилась**.

**Вывод:** сценарий «только поменял `nodeId` в update» **не подтверждён** — использовать **запасные сценарии** ниже или смотреть обновления 3x-ui / **API Docs** установленной панели.

### Запасные сценарии (всё через API)

1. **`POST …/inbounds/:id/copyClients`** — копирование клиентов с «старого» inbound (мертвая нода) на **новый** inbound, уже привязанный к живой ноде; затем при необходимости отключить старый inbound.
2. **Повторное создание клиентов** на новом inbound через `addClient` из данных вашей **БД приложения** (не панели): источник правды для «кого восстановить» — Postgres бота, панель — только исполнитель через API.
3. После смены ноды — для каждого затронутого пользователя **`getClientLinks`** / эквивалент, чтобы **vless** совпадал с панелью, и отправка через бота.

## Бот и конфигурация

- Панель для API: **`VPN_PANEL_URL`** — логично держать **внутренним** URL master (WireGuard / SSH tunnel / приватная сеть), не публичный пользовательский домен.
- Целевой inbound: **`VPN_PANEL_INBOUND_ID`** (если один «боевой» inbound на выдачу).
- Все операции с клиентами — **только методы REST**, как в [`PANEL_REST_API.md`](PANEL_REST_API.md).

---

## Ansible

- Ноды, регистрация, per-node inbound с remark и портами — как в репозитории (`ansible/3xui/`).
- Failover-логику и массовую рассылку ссылок **Ansible не заменяет** — это приложение (бот + воркер/крон + мониторинг).

---

## Краткий чеклист при инциденте

1. Подтвердить, что нода мертва (пробы + панель).
2. Выбрать живую ноду из пула.
3. Через API: либо смена привязки inbound (если подтверждена на вашей версии), либо `copyClients` / восстановление клиентов на inbound новой ноды.
4. Получить актуальные ссылки API и **разослать новые `vless://`** через бота.
5. Убрать мёртвую ноду из пула выдачи и из инвентаря при следующем деплое.

## Версионность

Поведение `nodeId` и миграций **зависит от версии 3x-ui**. Репозиторий целится в **v3.0.2**; при обновлении панели перечитать встроенные **API Docs** и при необходимости скорректировать этот документ.
