# Порты и hardening серверов (master и ноды)

Кратко: **master** — панель 3x-ui, nginx/TLS, Docker, SSH; **ноды** — обычно только прокси (Xray) и SSH, без публичной панели. Принципы SSH и фаервола на нодах те же, набор **входящих** портов сужаем до минимума под роль.

---

## Как устроен bootstrap (`ansible/bootstrap/bootstrap.yml`)

Два play’а и **один путь маркера** на хост: **`/etc/<slug>-bootstrap.done`**, где `<slug>` из **`DOMAIN_NAME`**. Пока файл есть — **повторная фаза на этом хосте не выполняется**.

**Фаза 1 — `hosts: all`** (master и ноды в inventory): при необходимости Python → факты → проверка маркера → если маркера нет: **`tasks/common/tcp-bbr.yml`**, **`docker.yml`**, **`ssh-key.yml`**, **`ssh-hardening.yml`**. На хостах из группы **`[nodes]`** (если она не пустая) сразу пишется маркер с **`phase=system`** — для нод отдельного nginx/certbot нет.

**Фаза 2 — только `hosts: master`**: нужен **`DOMAIN_NAME`** → nginx + certbot (**`tasks/master/nginx-certbot.yml`**) → маркер с **`phase=full`**.

Порядок SSH: **`SSH_PUBLIC_KEY`** в `authorized_keys` для **`ANSIBLE_SSH_USERNAME`** (в CI **`root`**); затем **`ssh-hardening.yml`**: отключение пароля и лишних методов, **`MaxAuthTries 3`**, **`PermitRootLogin prohibit-password`** для root; **UFW**: **default deny incoming**, **default allow outgoing**, профиль **OpenSSH**, включение UFW. На master во второй фазе — **Nginx Full** (80/443).

Итог для **первого** захода Ansible из GitHub: в **`MASTER_IP`** должен быть пароль **`root`**, пока bootstrap **ещё не выполнялся**; в одном прогоне в ключи добавляется ваш публичный ключ, затем парольный вход по SSH **отключается**. Дальше вход только по **`SSH_PRIVATE_KEY`** / вашей паре с машины.

Если вы хотите **сами первый раз** зайти на сервер по паролю с ноутбука: это возможно **до** первого успешного bootstrap (или на чистой машине до шага hardening). После bootstrap **пароль root для SSH больше не используется** — нужен ключ. Сброс доступа только через консоль провайдера или rescue-режим, если ключ потерян.

## Порты: что открываем и что закрываем (master)

### UFW (хост)

| Направление | Порт / профиль | Зачем |
|-------------|----------------|--------|
| Входящий, разрешён | **22** (профиль **OpenSSH**) | Администрирование по SSH после bootstrap. |
| Входящий, разрешён | **80, 443** (**Nginx Full**) | HTTP-челлендж и HTTPS для домена (**certbot**, reverse proxy на панель/приложения). |

Политика UFW по умолчанию после `enabled` — **всё остальное входящее снаружи не принимается**, пока не добавите правила вручную (например **2053** для прямого доступа к веб-панели 3x-ui без nginx — в текущем bootstrap **не** добавляется).

### Цепочка DOCKER-USER (iptables, из `tasks/common/docker.yml`)

Правила обрабатывают трафик **к опубликованным портам контейнеров** до того, как он уйдёт наружу с хоста:

| Действие | Суть |
|----------|------|
| Разрешить | **443**, **80** с любых адресов — типичный публичный веб. |
| Разрешить | **8000** только с диапазона **172.16.0.0/12** (docker bridge) — внутренние обращения к «API панели» на 8000. |
| Запретить | **8000** **не** с 127.0.0.1 — с интернета на порт 8000 **DROP** (не светим внутренний API панели наружу). |
| Плюс | **RELATED,ESTABLISHED** и **RETURN** в конце цепочки. |

Порты **VPN** (например входящий **443** на Xray, если он слушает не через nginx, или другие протоколы) в этом репозитории **явно не открываются** bootstrap’ом — их нужно проектировать отдельно (UFW +/или DOCKER-USER + схема «только nginx снаружи»).

## Ноды (отличие от master)

Типичная цель ноды — **проксирование трафика**, не веб-панель.

- **SSH 22** — открыт по той же логике, если на ноде прогоняете тот же набор ролей (ключ + hardening + UFW).
- **Публичные порты VPN** — только те, что реально нужны inbound’ам (часто один **443** / один порт на инстанс); лишнее не публикуем.
- **Панель 3x-ui на ноде** (если ставите полноценную панель-ноду): веб-порт либо только **loopback + SSH-туннель**, либо за ограниченным ACL/VPN, а не весь интернет, если нода «только релей».

Единого плейбука нод в репозитории пока нет — правила портов фиксируйте в том же духе: **минимум открытых входов**, всё остальное default deny.

## Как в целом должен выглядеть hardening серверов

1. **SSH**  
   - Только ключи для админского входа; **root** — `prohibit-password` или отдельный пользователь с `sudo` и запретом root-login — на выбор политики.  
   - Выключить пароли и лишние методы аутентификации (как в **`tasks/common/ssh-hardening.yml`**).  
   - По желанию: `AllowUsers`, другой порт SSH, `fail2ban` — пока не в репозитории, но уместно.

2. **Фаервол хоста (UFW или аналог)**  
   - Default **deny incoming**; явно **allow** только SSH и нужные сервисы (80/443, при необходимости порты VPN).  
   - Исходящие обычно разрешены (обновления, pull образов).

3. **Docker**  
   - Не публиковать внутренние API (как **8000** для панели) на `0.0.0.0` без необходимости; цепочка **DOCKER-USER** — дополнительный слой «что ушло в published ports».  
   - Образы с доверенных регистров, теги с дайджестами где критично.

4. **TLS и nginx**  
   - Публичный веб и панель (если за nginx) — **Let's Encrypt**, редирект HTTP→HTTPS где уместно (как в certbot в bootstrap).

5. **Хост и ядро**  
   - Автообновления безопасности (unattended-upgrades) — по желанию, в bootstrap пока не включено.  
   - BBR уже включается в bootstrap.

6. **Секреты и доступ**  
   - Пароли только для **первого** Ansible-прогона или консоли провайдера; в Git — только **`MASTER_IP`** / ключи как секреты, не plaintext в репозитории.
