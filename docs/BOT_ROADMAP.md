# Roadmap бота: 4–6 недель

Практический план развития **прикладного слоя** (Telegram-бот, Billing, Subscriptions, VPN-адаптер). Инфраструктура master/ноды, Ansible и watchdog описаны отдельно: **[`VPN_OPERATING_MODEL.md`](VPN_OPERATING_MODEL.md)**, **[`DEPLOY_BOT.md`](DEPLOY_BOT.md)**.

Ориентиры архитектуры и модулей — **`.cursorrules`** (границы Telegram / Users / Billing / VPN, транзакции, аудит).

**Зафиксированный этап MVP (без оплаты, готов к нагрузке):** **[`PRODUCT_STAGE.md`](PRODUCT_STAGE.md)** — 2026-05-17.

## Текущее состояние (база)

| Есть | Нет / заглушка |
|------|----------------|
| Выдача и продление через 3x-ui API, `vless://` на ноду | Реальный PSP (оплата всегда «успешна») |

| Ротация нод по лимиту (`VPN_INBOUND_CLIENT_LIMIT`, дефолт **200**) | — |
| Полный цикл teardown + redeploy (`scripts/reset_and_redeploy.sh`) | — |

**Не входит в этот roadmap** (отдельные решения продукта): подписка `/sub/` и Clash, split tunnel для `.ru`, WARP/NordVPN в панели — см. обсуждение в операционной модели; включать только при явной продуктовой задаче.

## Недели 1–2: платежи (PSP)

### Сделать

1. **Модель данных** (Prisma Migrate):
   - `Order` / `Payment`: статус, сумма, валюта, `planMonths`, `userId`, `idempotencyKey`, `providerPaymentId`, метаданные webhook.
2. **Контракт `PaymentProvider`** — вторая реализация (ЮKassa / Robokassa / Crypto — один PSP на старт), заглушка остаётся для `NODE_ENV=development`.
3. **Webhook-контроллер**:
   - проверка подписи провайдера;
   - идемпотентность по `providerPaymentId` / ключу webhook;
   - только после `paid` → `BillingService` → `SubscriptionsService.createSubscription` (или продление).
4. **Транзакция Prisma**: запись оплаты + выдача VPN; при ошибке панели — статус «требует вмешательства», алерт админу в Telegram, без повторной выдачи при повторном webhook.
5. **Сценарий в боте**: покупка ведёт на оплату PSP, не на мгновенную заглушку (заглушку оставить за feature-flag или env).

### Критерий готовности

- Успешный платёж в тестовом режиме PSP → одна подписка в БД, один клиент в панели, одно сообщение с `vless://`.
- Повторный webhook → без второй подписки.
- Ошибка панели после оплаты → запись в audit + понятное сообщение пользователю/админу.

## Недели 2–3: жизненный цикл подписки

### Сделать

1. **BullMQ job** (или cron): подписки с `expiresAt < now` и активным клиентом в панели.
2. Для каждой: `updateClient` / `enable: false` (или удаление по политике) через `VpnProvider`.
3. Запись в `AccessAuditLog`, опционально уведомление (уже есть `SUBSCRIPTION_ENDED` — не дублировать спам).
4. **Grace period** (опционально, 1–3 дня): только уведомления, отзыв после grace — через env.

### Критерий готовности

- Истёкший срок в БД → в течение N минут клиент не подключается в Xray.
- Продление до истечения → клиент остаётся активным, срок в панели совпадает с Postgres.

## Недели 3–4: тесты

### Сделать

1. **Unit**: расчёт срока, идемпотентность billing, выбор inbound при лимите (`LoadBalancerService`).
2. **Unit**: failover — сопоставление email после `copyClients` (суффиксы `_2`, `_*` на целевом inbound).
3. **Интеграция** (по возможности testcontainers): `SubscriptionsService` + mock `VpnProvider`.
4. CI: `npm test` в workflow перед/вместе с `deploy-bot`.

### Критерий готовности

- PR не ломает сценарии оплаты, выдачи и failover без ручного reset.

## Недели 4–5: админка в Telegram

### Сделать

1. Расширить `/admin` (только `TELEGRAM_ADMIN_ID`):
   - число активных подписок;
   - заполненность inbound’ов (клиенты / лимит);
   - последний failover (из audit или Redis).
2. Команды или inline: **ручная выдача**, **продление**, **отключить** — через `VpnAdminProvider`, с audit.
3. Не дублировать полный UI панели — только аварийные операции.

### Критерий готовности

- Оператор выдаёт ключ пользователю из бота без входа в веб-панель.

---

## Недели 5–6: тарифы и промокоды

### Сделать

1. Тарифы: вынести из захардкоженного `access-prices.ts` в **JSON env** или таблицу `Plan` (цена, месяцы, `limitIp`, label).
2. `PricingCatalogService` читает из одного источника; контент бота — label из каталога.
3. **Промокод v1**: `PromoCode` (% или дни, лимит использований, срок действия); применение в `PurchaseScene` до checkout.

### Критерий готовности

- Смена цен для white-label — без правки кода, только конфиг/БД + деплой.
- Промокод даёт скидку или бонусные дни один раз на пользователя (правило зафиксировать в коде).
